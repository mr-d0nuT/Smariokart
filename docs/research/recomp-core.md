## 0. 总览：原版架构一图流

```
$80:FF70 复位向量 (SEI→native模式, S=$1FFF, fastROM)
  └─ $80:803A 硬件初始化 (DB=$80; 关NMI/DMA/HDMA; $2100=$8F 强制黑屏)
       └─ $81:E000 全局初始化 (清WRAM $7E:2000+ / SRAM校验 / PPU初始化$80:8BEA
            / APU握手 / DSP-1复位(向$00:6000写$80×128) / 字符解压$81:E576
            / ★Mode7角度表构建$81:E4B3 ; $36=$001A ; $4200=$B1(NMI+自动手柄+V中断)
            ; $32=$0004, $48=$8F00 → 触发进入title)
  主循环 $80:8056 (每帧一次):
    ① JSL $81:E067  ← 转场/序列器（见§2）
    ② STZ $44       ← 清"NMI已发生"握手标志
    ③ LDX $36 ; JSR ($8197,x)  ← 按 $36 分发本帧状态主逻辑
  NMI $80:8000 (每垂直消隐):
    读$4210应答 → INC $34(全局帧计数) → JSR $80:B181(亮度渐变,见§6)
    → LDA $36 ; JSR ($81BF,x)  ← 按状态分发NMI侧渲染
```

**关键变量速查表**（JS 版应对应建模）：

| WRAM | 含义 |
|------|------|
| `$34` | 全局帧计数（NMI 里 INC） |
| `$38` | 各状态内部游戏帧计数（每个主状态处理器开头 INC） |
| `$36` | **当前模式**（屏幕状态号） |
| `$32` | **待切换模式**（非 0 = 有转场挂起） |
| `$48` | 渐变方向/累加器：>0 淡入中，<0 淡出中，0 静止 |
| `$015E` | 渐变步长（典型 $0060/帧） |
| `$0160/61` | 屏幕显示寄存器影子：$0160==$8000 表示完全淡出（强制黑屏） |
| `$44` | NMI→主循环 握手标志（$80:81DD 置 1） |
| `$64` | 全局节拍计数器（$85:84D1 每帧 INC） |
| `$1040` | title 界面闲置计时器（≥$0642 进 attract demo） |
| `$20/$22` | 手柄1/2 当前键况 · `$24/$26` 上帧 · `$28/$2A` 本帧新按(边沿) |
| `$6A/$6C` | **菜单确认用**边沿锁存（由 $85:92F9 门控复制自 $28/$2A） |

## 1. NMI / 帧循环结构（每帧做什么、什么顺序）

### 1.1 一帧的真实顺序

以状态 $04（title）为例（其余状态结构相同，仅换 NMI 处理器）：

```
[垂直消隐 NMI $80:8000]
 1. 读 $4210 应答 NMI
 2. INC $34                      ; 全局帧计数
 3. JSR $80:B181                 ; 亮度渐变步进 → 写 $0160, 高字节→$2100
 4. JSR ($81BF,x) x=$04 → $80:8237:
      - 检查 $44==0 才执行（防止同帧重复渲染）
      - DEC A ($FFFF) → STA $44   ; 通知主循环"NMI已过"
      - JSR $80:946E              ; OAM DMA：把 WRAM $00:0200 起的 $0220 字节
      │                            经 DMA ch0 → $2104(OAMDATA)，OAMADDR 先清零
      - JSL $85:809B              ; BG卷轴：$64/$65 → $210F(BG1HOFS)写两次；
      │                            $420C=$02 使能 HDMA ch1
      - JSR $80:81B5              ; 清尾：DP$42/$43→APU口$2142/$2143；
                                   ;   JSR $80:843C 读手柄(见§3)；JSR $80:9EB2
[主循环 $80:8056]
 5. JSL $81:E067                 ; 若 $32!=0 且淡出完成 → 执行转场(§2)
 6. STZ $44
 7. JSR ($8197,x) x=$04 → $80:80BA:
      - INC $38
      - STA $015E                 ; 设定渐变步长
      - JSL $85:8045              ; 精灵逻辑更新（槽位速度→位置→OAM 构建）
      - JSR $80:853D              ; title 输入处理（见§3）
```

要点：**原版是"NMI 侧做呈现（OAM/卷轴/音频/输入），主循环侧做逻辑"的双段模型**，
两段靠 `$44` 握手。JS 版若用 requestAnimationFrame 单循环，等价于把 1-4 当
"帧首渲染提交"、5-7 当"帧末逻辑"，但必须保持输入读取发生在渲染提交之后、逻辑之前。

### 1.2 各状态的 NMI 处理器（$80:81BF 表）

| $36 | NMI 处理器 | 行为 |
|-----|-----------|------|
| $00/$1A | `smk_8081DD` ($80:81DD) | 仅置 $44=1 唤醒主循环（黑屏期无渲染） |
| $04 title | `smk_808237` ($80:8237) | OAM DMA + BG卷轴/HDMA + 清尾 |
| $06 driver select | `smk_80824D` ($80:824D) | OAM DMA + JSL $85:90D7（菜单专用渲染） + 清尾 |

### 1.3 各状态的主处理器（$80:8197 表）

| $36 | 主处理器 | 行为 |
|-----|---------|------|
| $02 race | `smk_808067` ($80:8067) | `LDA $0162/BMI` 跳过；INC $38；（后续比赛逻辑**尚未重编译**） |
| $04 title | `smk_8080BA` ($80:80BA) | INC $38；设 $015E；JSL $85:8045 精灵更新；JSR $80:853D 输入 |
| $06 | `smk_8080CA` ($80:80CA) | INC $38；`$015E=$0060`；JSL $85:90B1 菜单逐帧逻辑 |
| $14 mode select | `smk_808174` ($80:8174) | INC $38 后调 $08:8C1A（字体/调色板 DMA、光标精灵、亮度=$0F） |

【我们JS版可能缺失或简化】
- **双段帧模型**：JS 版大概率单循环直呼 update+draw，缺 $44 握手与"NMI 侧先提交渲染"
  的次序——影响不大但要保持"输入在逻辑前、渲染提交在逻辑后"的次序。
- **OAM 影子缓冲**：原版先把精灵写进 WRAM $0200-$041F（含 $0400 高位表），再一次性
  DMA。JS 版直接画即可，但若要做"逐字节对拍调试"，建议保留一份等价的 OAM 影子数组。
- **BG 卷轴写两次**：`$64/$65 → $210F` 低/高字节各写一次是硬件协议，不是两次赋值。
- **比赛($02)整层缺席**：$80:8067 只剩 INC $38——比赛内逻辑完全没有重编译（见§4）。

## 2. 主状态机：$81:E000 序列器（全部状态与转换条件）

### 2.1 核心机制（来自 $81:E067 忠实移植 + 流程文档实机追踪）

- `$32` = 待进入模式；`$36` = 当前模式。
- **转场只在「`$32 != 0` 且 `$0160 == $8000`（已完全淡出到强制黑屏）」时触发**。
  切屏的正确姿势是：`$32 = 目标模式` 并启动淡出（`$48=$8F00, $015E=$0060`)，
  等渐变走完，序列器自动进入。
- 转场体（`smk_81E067`, $81:E067）逐条做了什么：

```c
STZ $420B / STZ $420C     // 关 DMA/HDMA
LDA $36 → STA $0106       // 保存旧状态
STZ $36 / STZ $D0         // 清当前状态与子状态指针
SEI / STZ $4200           // 关 NMI（转场期间独占 CPU）
LDX $32 ; JSR ($E049,x)   // ★执行目标模式的 INIT 处理器
LDA #$0001 → STA $48      // ★置淡入触发（下一帧起亮度从 $8000 爬回 $0F00）
LDA $32 → STA $36         // 正式切换
STZ $32
CLI / LDA #$B1 / STA $4200 // 恢复 NMI+自动手柄
```

### 2.2 模式→INIT 表（$81:E049，索引=$32）

| $32 | INIT | 已知含义 |
|-----|------|---------|
| $00 | $E0AC | 黑屏/空（boot 与 fade 中转用） |
| $02 | $E126* | **race**（比赛；*表中指向 $E126，流程文档实测 attract 从 demo 进入） |
| $04 | $E12E | title |
| $06 | $E2F3 | driver select（选车手/1P-2P） |
| $08 | $E13E | class/cup 选择（50cc + 蘑菇/花/星杯） |
| $0A | $E22B | （未实测；按 SMK 结构应为 Match Race 相关） |
| $0C | $E388 | （未实测） |
| $0E | $E390 | （未实测） |
| $10 | $E398 | （未实测；Battle 相关候选） |
| $12 | $E258 | （未实测） |
| $14 | $E34F | mode select（GP/TimeTrial/Match/Battle 模式单） |
| $16 | $E0AC | 同 $00（占位） |
| $18 | $E136 | （未实测） |

*`smk_init.c` 把 $81:E126 注释为"character select"，而 `functions.h` 把 $80:80CA 注释为
"character select"、把 $80:174 注释为"mode select"；流程文档以实机为准：**$06=driver
select、$08=class/cup、$14=mode select、$02=race**。JS 版请采用实机语义，勿信旧注释。*

### 2.3 实测流转序列（headless 驱动原生 ROM，tools/bizhawk）

- 冷启动：f1-126 $36=$00 → f127-167 $1A → f168-208 $00 → f209 起 $04（title）。
- **title 输入门**：只有当淡入完成（`$0160` 到 $0F00，约 f360）后才接受输入；
  淡入中的按键一律忽略。
- 交互路径：title --(确认键)--> $06 driver select --(双人确认门)--> $08 class/cup --> $02 race
  （snes9x 实测 f209/f599/f896/f1045；LakeSnes 修复 WRAM 填充后 f209/f599/f826/f1045）。
- attract 循环：title 闲置计时 `$1040` 数到 $0642 → 淡出(f1891) → $02 demo 比赛(f1973+)；
  demo 中按 START 回 title。
- **没有独立 Nintendo logo 屏**（©1992 就画在 title 上）；JS 版直接跳到 $04 是跳过了
  $00→$1A→$00 三段黑屏初始化链。

### 2.4 title 的确认键真相（踩坑记录，JS 版直接抄答案）

- 最终结论（LakeSnes trace-diff 定案）：**确认就是 START 单键**（边沿）。
  此前"Select+Start""Start+Y"均为误判（键盘 Space=Y 导致 Start+Y 里起作用的其实是 Start）。
- title 内部还有两层历史遗留门（逆向时曾误认为入口键）：
  1. `$0E68` 输入门：全 ROM 只有一次 `STZ $0E68`（$81:E0BD/$E0C0），没有任何静态置位指令
     ——它实际恒为 0，title 输入处理 `$80:853D` 开头的 `LDA $0E68/BEQ` 在 attract 下永远关门。
  2. `$80:8559 BIT #$2000`（Select）条件检查。
- 重编译壳 `smk_80853D` 的简化做法：绕过两道门，直接查 START 位并
  `$32=$0014; $015E=$0060; $48=$8F00`（发起去 mode select 的转场）——**这是 JS 版应该采用的语义**。

【我们JS版可能缺失或简化】
- **必须补：淡出门控**。JS 版切屏八成是立即 switch(screen)。原版任何切屏都要先完整淡出
  （`$0160`==$8000）才允许 INIT 执行；这直接影响手感节奏与"按键被吞"的表现。
- **必须补：INIT 后 `$48=1` 自动淡入**（步长取 $015E）。
- **启动序列**：建议至少保留 title 前的黑屏期与输入门（淡入完成前忽略输入），
  这是"原味手感"的一部分。
- attract demo 整条时间线（$1040 阈值 → demo → START 返回）在 JS 版通常没有。

## 3. 输入处理细节

### 3.1 读入手柄（NMI 尾部，$80:81B5 → $80:843C / 忠实叶 $80:8445）

```c
// 每个手柄 x∈{0(1P),2(2P)}：
cur = bus_read16(0x80, 0x4218 + x);        // 自动手柄寄存器
wram[$20+x] = cur;
edges = (cur ^ wram[$24+x]) & cur;         // ★上升沿 = (本帧 XOR 上帧) AND 本帧
wram[$28+x] = edges;
wram[$24+x] = cur;                         // 存上帧
// 忠实版额外含软复位路径：
if (wram[$0E32]!=0 && wram[$0E50]==0 && wram[$32]==0 && (edges & $9000))
    → JML $80:85FD                          // Start(+B) 组合软复位
```

**按键位约定（$4218 读出的 16 位，MSB 在前）**：
B=$8000, Y=$4000, Select=$2000, **Start=$1000**, Up=$0800, Down=$0400,
Left=$0200, Right=$0100, A=$0080, X=$0040, L=$0020, R=$0010。
（例：隐藏删档组合 Y+A+L+R == $40B0；确认键判定 `AND #$9000` = **B 或 START**。）

### 3.2 菜单输入提交门（`smk_8592F9`, $85:92F9 —— autogen 已逐字节验证）

```c
if (wram[$48] != 0) { wram[$6A]=0; wram[$6C]=0; return; }   // 渐变进行中→吞输入
SEP; if ((wram[$0161] /*亮度*/ ^ 0xFF) >= 0x0F 不成立即 $0161!=$0F) 同上吞输入;
// 屏幕完全亮起后才放行：
wram[$6A] = wram[$28];    // 1P 边沿锁存
wram[$6C] = wram[$2A];    // 2P 边沿锁存
switch (wram[$36]) {
  case 4: return;                                  // title 无后续分发
  case 6: if (wram[$2C]==4 && wram[$2E]==2) return; // 双人已锁定→不再进选择逻辑
          /* fallthrough */ JSR $85:9336;
  default: JSR $85:9336;                           // 菜单输入动作分发
}
```

### 3.3 driver select 确认链（$85:90B1 主逻辑内的关键叶子，流程文档 trace 定案）

- `$85:9487`: `LDA $6A / ORA $6C / AND #$9000 / BNE` —— 确认键 = **B 或 START 边沿**（任一手柄）。
- 第一次按：锁定当前光标车手（`$70,x=1`，播 SFX，音效命令写 `$002E`）；
- 第二次按（`$70,x==1`）→ `$952C`：置 `$70,x=2`（该玩家完成）。
- `$85:965B` 推进门：`LDA $70/CMP #2` **且** `LDA $72/CMP #2` 都通过才继续
  —— **1P 和 2P 都必须到达"完成"状态**，随后 64 帧定格（计数器 $96 递减到 $40）再切 $08。

### 3.4 游戏人数的"玄学"来源 —— 未初始化内存语义（★重要教训）

`$81:E46A` 对 `$2E`(游戏模式) 的钳制：

```c
$2E &= 0xFFFE; if ($2E >= 5) $2E = 2;   // 即垃圾值→2(1P 游戏, 2P 视为已完成)；干净的 0 保持 0(2P)
```

开机 WRAM 内容决定 1P/2P 默认！snes9x/真机开机上电填充非零（0x55 → 每字 $5555 →
$2E=2），LakeSnes 曾 memset(0) 导致 $2E=0、永远等待"2P 确认"。修复 = 上电填充 0x55。

【我们JS版可能缺失或简化】
- **RAM 上电必须填 0x55 而不是 0**——这不是玄学，是被游戏读取的未初始化语义，
  直接改变菜单流程行为。JS 版 `new Uint8Array(0x20000)` 默认全 0，**必踩同一个坑**。
- 边沿检测公式 `(cur^prev)&cur` 与三组影子变量（当前/上帧/边沿）要照搬。
- **两级输入门**（渐变中吞输入 + 完全亮起才锁存到 $6A/$6C）：JS 版菜单若直接读 keydown
  事件，会在转场瞬间误触发确认——需要同样的"亮起才接受"闸门。
- 双人确认门 + 64 帧定格延迟：JS 版单人游玩也要模拟"2P 已完成"的默认态（对应 $2E=2 语义）。
- 软复位路径（Start+B 且无转场挂起 → 回到安全状态）与删档彩蛋（title 按 Y+A+L+R，
  $84:FD25，YES/NO 光标 $7B，擦 SRAM $30:$6000-$67FF）：低优先级但属于原版行为。

## 4. Mode7 比赛内真实机制 —— 现状与已有线索

### 4.1 ⚠️ 诚实的现状：比赛物理层不在本项目任何 C 文件里

逐一核对 `functions.h` 总表与全部 RECOMP_PATCH（共 57 个函数）后确认：
**车速/加速度/转向/漂移/道具/圈数判定/排名的常量与公式一个都没有被重编译。**
`smk_autogen.c` 的 19 个叶子全是菜单/attract/OAM/PPU 管线；`smk_boot.c` 的 $02 主处理器
只剩 `INC $38`。目前项目里"能玩比赛"靠的是 **SMK_REALFRAME=1 整帧解释执行真 ROM**
（LakeSnes 周期精确模拟 + 真 DSP-1），而不是翻译出来的代码。

因此本节给出的是**本项目能提供的全部比赛相关素材**，以及它们对 JS 版的意义。

### 4.2 已重编译的比赛相关数学：atan2 与角度表（可直接抄给 JS）

#### `smk_81F722`（$81:F722，静态实现于 smk_init.c）— 8-bit atan2

- 输入 16 位有符号 Δx/Δy；输出 8-bit 角度：$00=0°、$40=90°、$80=180°、$C0=270°。
- 流程：
  1. 特例 y==0：x<0→$C0 否则 $40；x==0：象限奇数→$80 否则 $00；都 0→$00。
  2. 象限编码：y<0 +1，x<0 +2，若 |x|<|y| 再 +4（交换标志）并互换使 larger=大者。
  3. 同时折半缩小直到 larger < $100。
  4. ratio = min(255, smaller*256 / larger)（原版用硬件除法器 $4202-$4205 系列）。
  5. 查**解压出来的 atan 基表**（256 字节，源数据 $C6:1F46 → 解压到 $7F:0000）得基角。
  6. 象限修正：negate_flags[8]={FF,0,0,FF,0,FF,FF,0} 决定是否取负；再加
     quadrant_offsets[8]={$40,$40,$C0,$C0,$00,$80,$00,$80}。
- JS 建议：把 256 字节基表作为常量资源导出（可从 ROM $C6:1F46 用原版解压器生成一次），
  然后 1:1 移植上面六步——保证与原版角度量化完全一致（ Kart 朝向/AI 瞄准都依赖它）。

#### `smk_81E4B3`（$81:E4B3）— 64×64 Mode7 角度查找表

```c
for (row=0..63) for (col=0..63)
    angle = (col>=row) ? atan2_f722(row,col)
                       : (uint8_t)(0x40 - atan2_f722(col,row));  // 镜像对称
// 结果 4096 字节存 $7F:9000
```

- 该表是原版比赛引擎把屏幕偏移映射为赛道方位角的核心 LUT（配合 DSP-1 坐标变换使用）。
- JS 建议：同样离线生成一张 4096 字节表内嵌进 bundle；运行时查表代替 Math.atan2，
  既省性能又和原版量化误差一致（AI 行为才会一样）。

### 4.3 比赛的帧级表现（来自流程文档 + 壳代码注释的实证）

- **M7 光栅初始化确实会跑**：比赛设置路径 `$81:F7F1 → $FB7E`，在 PC `81:FB83` 置
  `$A4=6`，配置**逐扫描线 M7 HDMA 指针**（每行重写 $211B-$2120 矩阵实现透视）。
- **比赛开场固定序列**：屏幕复位例程 `$84:F38C`（`STZ $420C` 关 HDMA、`$2100=$80`
  强制黑屏、清窗口/色彩运算/OAM）→ 之后若干帧里重新使能 HDMA 并触发淡入
  （`$48>0`，经 §6 的 NMI 渐变爬回 $0F00）。**淡入未完成期间画面就是黑的**。
- **屏幕闪白/闪黑效果** `smk_818902`（$81:8902）：`$1F06` 的 bit7 置位时，
  `$2100=$08`（黑）→ 忙等 16 次 DEX → `$2100=$0F`（全亮），单帧闪烁
  （比赛开始信号灯/闪电类演出可用同款手法）。
- **DSP-1**：映射 $00-1F:$6000-$7FFF；init 向 $00:6000 连写 $80 ×128 复位。
  所有 M7 世界坐标↔屏幕坐标变换跑在协处理器上。JS 版要么实现 DSP-1 的 M7 指令集
  （MULT/DIV 类坐标变换），要么用等价矩阵数学——**但必须逐扫描线应用矩阵**
  （透视正确性依赖 HDMA 每行改写 $211B-$2120）。

【我们JS版重大缺口（优先级最高）】
1. **整个比赛玩法层**（卡丁车对象状态机、油门/刹车/漂移物理、道具盒与道具效果、
   圈数/检查点、名次排序、AI 车、HUD 计时）在本重编译项目中**零覆盖**——JS 版无法从这里
   抄到数值。可行路线：(a) 从 Yoshifanatic1/Super-Mario-Kart-Disassembly 或 jvipond 的
   trace 反汇编提取 bank $80/$82 卡丁车代码与数据表；(b) 用本项目已有的
   "oracle diff harness"方法（autogen.py + LakeSnes 逐字节对拍）批量翻译比赛函数；
   (c) 至少先从 LakeSnes 运行时抓 WRAM 关键量（速度、角度、圈数计数器地址）建立观测。
2. **逐扫描线 HDMA**：JS 版如果只做"每帧一次的 M7 矩阵"，透视地平线会是错的；
   必须 per-scanline 更新矩阵（这正是本项目壳路径翻车的根因，见 §1/§6）。
3. **DSP-1 语义**：注意其输出格式（坐标的小数定位、符号约定）与普通定点不同。

## 5. 对象/演出系统（菜单与 attract 共用的通用件）

这些是 `smk_autogen.c` 逐字节验证过的通用机构，JS 版的菜单/演出层可以直接对照实现：

### 5.1 对象槽与字段布局（DP 相对寻址 + X=对象序号）

| 偏移 | 含义（由用法反推） |
|------|-------------------|
| `$10+X` | 标志字：bit5($0020) 参与 z-sort 条件；bit14($4000) 会被 ORA 置位 / $BFFF AND 清位 |
| `$12+X` | 动画/图案索引（→ 表 $80:B837[Y]） |
| `$1C+X` / `$44+X` | 当前值/目标值 —— 插值对（见 5.3） |
| `$18+$2A+$92+$22+X` | 出生参数块字段（位置/速度等，见 5.4） |
| `$2C+$6C+X` | 由 $81:B9A8 构建的半字节表（高/低 nibble | $80、|$10，疑似 HDMA 表构建） |
| `$40/$42`@$1040/$1042 | attract 闲置计时器 / 阶段号（见 5.5） |
| `$5A/$5C/$5E+X` | 定时器组（$80:F90A：ASL 测 bit15→负则免减；否则递减 $5E 或 $5C；归零分支触发 $10+X 的 $BFFF/$4000 位操作——定时事件调度） |
| `$88/$8C+X` | 速度槽：从表 [$16+$18+$1A+$1C+Y] 取 16 位数 **ROL×3 = ×8** 后写入（$80:86A0，单位换算：表值×1/8 像素） |
| `$A4+X` | 类型字段（CMP #2 分支）；`$AC+X` 有符号判负 |
| `$C0+X` | **z-sort 深度键** |
| `$C6+X` | 三角波计数器（见 5.6） |
| `$C8+X` | 远程处理索引（负数跳过；喂给 $85:DFB4） |
| `$B8` | 当前对象 id（多个例程先 LDX $B8） |
| `$E6+X` | z-sort 链接游标 |

### 5.2 链表 z-sort（`smk_80A01F` → `smk_80A027`）

遍历 DB:$010C/$010E 的双向链（prev/next 表，Y=节点），比较深度键 $C0+X，
把新节点插入排序位置（大于当前键则继续走链），同步维护 $E6 游标。
**JS 建议**：每帧对可见对象按 depth key 做稳定插入排序再绘制；键即 $C0 字段语义（Y 坐标或距离）。

### 5.3 朝目标插值器（`smk_858EE9` + 脚本表）

- 脚本指针 `$75`（步进 2，到 $0010 归零）→ 表 `$85:8FE9[X]` 取对象 id → X。
- 每次调用把 `$1C+X` 向 `$44+X` 逼近 1（小于目标 INC，大于 DEC，相等则推进脚本）。
- **匀速逐帧逼近**，不是缓动。JS 建议：菜单光标滑动/数字滚动用 moveToward(cur,target,1)。

### 5.4 出生参数装载（`smk_858FB8`）

指针表 `$85:8FF9[Y]` → 连续 5 个 16 位字分别装入 `$18/$1C/$2A/$92/$44 +X`，`$22+X` 清零。
JS 建议：对象工厂读参数块表（position/target/misc/speed/goal 五元组）。

### 5.5 attract 导演（`smk_858B7A`）

- 前提 `$48==0`（无渐变进行）；先调插值器 5.3；
- `INC $1040`（title 闲置计时）；与阈值表 {$00D2, $01F2, $0452, $046A, $053A, $0592}
  比对，命中任一则 `INC $1042`（阶段号）；阶段号 ASL → 跳表 $85:8BB4 分发表演。
- **绝对时间轴驱动**（约 210/498/1106/1130/1338/1426 帧处触发事件）。JS 建议：attract
  用 timeline 数组 [{frame, action}] 实现。

### 5.6 三角波振荡器 + 图块翻转动画（`smk_80B7EB`）

```c
c = $C6+X;
if (c == 0)     { c = $80:B847(); store; return; }              // 种子初始化
else if (c < 0) { if (++c != 0) { store; return; }               // 负数向上走
                  c = $80:B847(); store; tilemap词=$2525; }      // 过零(负→0)
else            { if (--c != 0) { store; return; }               // 正数向下走
                  c = ~$80:B847()+1; store; tilemap词=$35A9; }   // 过零(正→0)，取负
```

计数值在 ±种子 间往返（三角波）；仅在**过零**时调用 $80:B847 取新种子，并把 $7E:3A80[X]
处 BG tilemap 词交替写成 $35A9 / $2525（两种 tile 交替 → 闪烁/波动动画）。
JS 建议：相位计数器 + 过零回调换贴图的通用动画件。

### 5.7 VRAM 装载作业队列（生产者 `smk_808D83` / 消费者 `smk_81CB35`）

- 生产者（主循环侧）：最多 8 个作业；每作业 12 字节写入 $0EA0+Y：
  源地址（低/高，高位从表 $8DD1/$8DE1/$8DF1[X] 查）、固定 $407F 尺寸/模式词×2、
  目标 = 基址+$0100 / +$0200 两路；队列写指针 `$4A` 每次 +12（TYA;ADC #$000C）。
- 消费者（NMI 侧）：VMAIN=$80，DMA ch0 mode=1 → $2118(VMDATAL)，按 $4A 从后往前逐条
  设置 VRAMADDRA + 源 + 触发，最后 STZ $4A。
- JS 建议：这就是"本帧产生的图形上传任务延到帧尾统一执行"的模式——JS 无需照搬，
  但若做逐字节对拍调试，值得保留同构队列。

### 5.8 PPU 影子寄存器批量上屏（`smk_808BBF`，M=1 X=1）

每帧把影子表按 X 偏移推到硬件：`$016A+X→$2131(CGADSUB)`、`$016C/+2/+4+X→$2132(COLDATA)×3`、
`$0108+X→$2125(WOBJSEL)`、`$014E+X→$212E(TMW)`、`$017A+X→$2130(CGWSEL)`。
JS 建议：维护一份 PPU 状态对象，集中提交渲染配置，别散落在各 update 里。

## 6. 渐变/亮度系统（一切转场的底层）

`smk_80B181`（$80:B181，忠实移植，NMI 每帧调用）：

```c
int16 b = $48;
if (b > 0) {  result = b + $015E; if (result >= $0F00) { $48=0; result=$0F00; } else $48=result; }
else if (b < 0) { result = b - $015E; if (!(result & 0x8000)) { $48=0; result=$8000; } else { $48=result; result &= 0x7FFF; } }
else result = $0160 (不变);
$0160 = result; $2100 = ($0161 = result >> 8);   // 高字节即 INIDISP
```

- 淡入终值 $0F00（亮度 15 可见）；淡出终值 $8000（强制黑屏）——$0160==$8000 正是 §2
  序列器的放行条件。
- 典型步长 $015E=$0060/帧 → 约 63 帧完成一次全程渐变；title 的 $80:80BA 每帧刷新
  $015E（重编译壳写了 $0040，原值为 $0060）。
- **INIDISP 只在有变化时才被游戏写**（约 900 帧 15 次写）——所以壳模型若不逐帧跑这个
  NMI 函数，画面就停在黑屏。这正是壳路径下"比赛永远黑屏"的根因（流程文档 2026-06-03b 定案：
  淡入触发 `$48>0` 从未发生），最终用 SMK_REALFRAME 整帧解释绕过。

【我们JS版可能缺失或简化】
- JS 版几乎肯定缺这套**有符号累加器 + 步长变量 + 终值门控**的渐变机。建议封装：
  `fade(dir, step)` / 每帧 `tickFade()` / `isFadedOut()`，并把所有切屏 API 改成
  "请求式"（set pending + 等淡出）而非立即切换。

## 7. 给 JS 版的补全清单（按优先级）

1. **P0 — 上电 RAM 填 0x55**（§3.4）：一行改动，避免菜单流程行为性差异。
